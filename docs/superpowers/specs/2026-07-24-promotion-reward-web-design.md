# 自动宣传审核与奖励回收 — 设计文档

- 日期:2026-07-24
- 涉及模块:`mod-promotion-reward`、`mod-redemption-code`、`mod-reward-template`
- 目标:玩家网页提交宣传材料,系统先发奖励,管理员后审,无效时精确追回并按连续次数封号

## 一、目标与已确认规则

### 1.1 业务目标

玩家使用游戏账号登录 Web 页面后,可以提交宣传图片或公开论坛链接。系统完成基础自动检查后先发放奖励;管理员随后审核。审核通过后奖励永久保留,审核无效则追回本次奖励,连续 3 次无效后封禁账号。

### 1.2 已确认决策

- 主系统采用 Web;游戏内执行由 worldserver 中的 C++ 模块负责。
- 玩家直接使用游戏账号和密码登录 Web;Web 不保存明文密码。
- 奖励模式由数据库配置,同时支持 CDK 和直接物品。
- 每个账号每日上限、每个 IP 每日上限以及任务级上限均可配置。
- 论坛链接允许所有公开网站,但必须无需登录访问,且页面标题或正文命中配置的服务器名称/关键词。
- 自动检查只是预检,管理员审核结果是最终结果。
- CDK 不绑定账号或角色;实际使用 CDK 的角色作为奖励受益人和追回对象。
- CDK 可以被转发;自动宣传 CDK 以首次实际兑换者为准,不保证一定由提交者本人兑换。
- 自动生成的宣传 CDK 每个只允许使用 1 次;兑换码数据不删除,保留审计记录。
- 直接物品奖励必须按实际物品 GUID 记录并追回。
- 无效次数按账号统计;连续 3 次无效封号,审核通过后连续无效次数清零。

## 二、现状核实

### 2.1 `mod-redemption-code` 可复用的记录

现有 `_奖励_兑换码` 表包含 `兑换角色`、`兑换账号`、`兑换IP` 字段。`RedemptionCodeMgr::RecordCodeUsage()` 会把实际角色 GUID、账号 ID 和 IP 写入这些字段,因此无需为宣传 CDK 增加账号/角色绑定字段。

现有记录是逗号分隔的累计字段,能够定位一次性 CDK 的实际兑换角色,但不是带时间和奖励明细的规范化事件表。因此本设计增加宣传业务流水,用途是关联提交、保存兑换前后状态和执行回滚,不是限制 CDK 使用者。

### 2.2 当前宣传 CDK 的回滚影响

`PromotionRewardMgr::RedeemPromotionCode()` 当前会:

1. 读取角色宣传天数并计算新等级。
2. 删除旧宣传神器。
3. 创建新的宣传神器。
4. 增加宣传天数并保存。
5. 由兑换码模块发放宣传 CDK 对应的额外奖励。

因此审核无效时不能只删除新物品,必须保存并恢复兑换前宣传天数、旧宣传神器和本次新增奖励。

## 三、总体架构

```text
玩家浏览器/手机
        │ HTTPS
        ▼
Web API + 玩家页面 + 管理员审核页面
        │
        ├── 图片对象存储/文件存储
        ├── auth.account 只读账号校验
        └── 宣传提交、审核、发奖队列数据库
                         │
                         ▼
               worldserver 模块消费者
                 ├── mod-promotion-reward
                 ├── mod-redemption-code
                 └── mod-reward-template
                         │
                         ▼
          发放、记录、追回、连续无效封号
```

Web 服务不直接修改背包、物品、宣传天数或封号状态。Web 只创建提交和发奖请求,由 worldserver 模块执行游戏状态变化,避免缓存不同步、重复发奖和 Web/游戏进程同时修改数据。

## 四、业务流程

### 4.1 登录与提交

1. Web API 使用现有游戏账号密码摘要校验账号,建立安全会话。
2. 玩家选择图片或论坛 URL,提交任务。
3. Web API 按账号、IP、任务和时间窗口检查每日次数。
4. 图片检查文件魔数、格式、大小、解码和重新编码;数据库只保存哈希与存储键,不把原图作为 SQL 大字段。
5. URL 只允许 HTTP/HTTPS。请求必须阻断内网、回环、云元数据和 DNS 重绑定地址,限制超时、响应大小和跳转次数。
6. 服务器抓取无需登录的 HTML,检查标题/正文关键词。动态脚本页面无法预检时转为待人工审核,不能直接判定无效。
7. 创建 `PENDING_REVIEW` 提交记录和幂等发奖请求。

### 4.2 预发奖励

由 worldserver 消费发奖请求:

- `CDK` 模式:生成唯一 CDK,插入现有 `_奖励_兑换码`,奖励次数固定为 1,注释包含宣传提交 ID,等待玩家正常兑换。
- `ITEM` 模式:由 worldserver 直接创建物品,记录每一个新物品 GUID。

发奖请求必须带唯一 request ID。重复消费只能返回原结果,不能再次生成 CDK、物品或奖励。

### 4.3 CDK 兑换记录

玩家使用 CDK 后,`mod-redemption-code` 继续写入现有兑换记录。宣传模块通过兑换完成回调或等价的同步记录动作创建宣传兑换流水,保存:

- CDK 与宣传提交 ID;
- 实际兑换角色 GUID、账号 ID、兑换时间;
- 实际奖励 ID;
- 兑换前和兑换后的宣传天数;
- 被删除的旧宣传物品与新建物品 GUID;
- 奖励模板产生的新增物品 GUID及可逆资源快照;
- 当前回滚状态。

此流水不改变 CDK 的自由使用规则,只负责后续审计和回滚。

### 4.4 管理员审核

- `APPROVED`:提交结束,奖励流水转为 `FINAL`。
- `REJECTED`:提交进入追回队列,写入审核理由,账号连续无效次数加 1。
- 审核结果必须幂等;已审核记录不能重复发奖、重复追回或重复累计。
- 审核通过后账号连续无效次数清零。
- 连续无效次数达到 3 时,由 worldserver 执行踢出和账号封禁,并写入审计日志。

## 五、数据库设计

### 5.1 world 数据库:任务配置

保留现有 `_宣传奖励系统` 作为兼容配置,新增或扩展任务配置表,至少包含:

- `任务ID`、名称、启用状态;
- `奖励模式` (`CDK`/`ITEM`);
- CDK 奖励组、需求 ID、奖励 ID;
- 物品 entry、数量及角色绑定策略;
- 账号每日上限、IP 每日上限、任务每日上限;
- 服务器名称与关键词集合;
- 连续无效封号阈值,默认 3;
- 图片大小/格式和 URL 检查参数。

### 5.2 characters 数据库:提交与流水

新增自定义表,建议包括:

- `_宣传提交记录`:账号、角色、IP、提交类型、图片存储键/规范化 URL、SHA-256、预检结果、审核状态、审核人和理由;
- `_宣传奖励流水`:提交 ID、发奖模式、CDK、奖励 ID、物品 entry、发放状态、撤销状态和幂等 request ID;
- `_宣传兑换流水`:CDK、实际兑换角色、兑换前后宣传天数、旧/新物品 GUID、额外奖励快照和回滚状态;
- `_宣传账号统计`:账号每日计数、IP每日计数、连续无效次数、封禁处理状态;
- `_宣传审核日志`:管理员操作、原状态、新状态、理由和时间。

图片正文放在受控文件/对象存储中,数据库只保存元数据和内容哈希。

## 六、追回策略

### 6.1 CDK 未使用

通过 CDK 关联流水把兑换次数置为 0 或写入撤销状态,不删除 `_奖励_兑换码` 行。

### 6.2 CDK 已使用

1. 从兑换流水或 `_奖励_兑换码.兑换角色` 找到实际使用角色。
2. 删除本次创建且仍存在的宣传物品和奖励物品。
3. 恢复兑换前宣传天数。
4. 恢复被升级流程删除的旧宣传神器。
5. 追回其它可追踪奖励。

如果物品已被销毁、消耗或无法确认归属,标记为 `RECOVERY_DEBT`,冻结该账号后续自动宣传奖励,交管理员处理;禁止按 entry 删除玩家全部同类物品。

### 6.3 直接物品模式

只按本次发奖流水保存的 item GUID 回收,不按物品 entry 全表扫描,也不影响玩家原有同类物品。

## 七、安全与风控

- 不保存游戏明文密码;登录接口限速、防爆破并记录审计。
- IP 计数只信任可信反向代理传递的真实地址;不把单一 IP 作为自动封号依据。
- 图片按魔数和解码结果验证,重新编码后存储,随机文件名,不放在可执行 Web 根目录。
- URL 预检阻断 SSRF、私网地址、非 HTTP 协议、恶意跳转和超大响应。
- 账号/IP/内容哈希/规范化 URL 多维去重,所有发奖和审核动作使用幂等键。
- 管理员使用 RBAC,驳回必须填写理由,所有审核和回收操作追加审计日志。

## 八、验证计划

### 8.1 Web/API

- 游戏账号密码校验、会话和权限测试;
- 账号/IP/任务每日次数边界测试;
- 图片格式、重复图片、恶意文件和存储权限测试;
- 公网 URL、关键词、跳转、私网地址和动态页面预检测试;
- 重复请求不会重复发奖。

### 8.2 worldserver/模块

- CDK 单次使用和兑换记录回调测试;
- 直接物品 GUID 记录测试;
- 宣传神器兑换前后状态快照和完整回滚测试;
- 已销毁物品进入追回欠账,不误删同类物品;
- 审核状态重复提交、连续无效次数和封号幂等测试。

### 8.3 联调

- Web 创建提交 → worldserver 发奖 → 玩家兑换 → 管理员通过/驳回;
- CDK 未使用、已使用、奖励已消耗三种追回路径;
- worldserver 暂停或重启期间队列重试不重复发放;
- 数据库行、worldserver 日志和账号最终状态一致。

## 九、非目标

- 首版不使用 AI 自动决定图片是否合格;自动系统只做技术预检,最终由管理员审核。
- 首版不做 Qt 主客户端;如有需要,后续 Qt 仅作为调用同一 Web API 的管理员工具。
- 首版不把图片二进制直接存入 AzerothCore 三库。
- 不删除或覆盖现有 `_奖励_兑换码` 历史记录。

## 十、实施边界

实现阶段需要:

1. 扩展 `mod-promotion-reward` 的发奖、兑换流水和回滚接口。
2. 在 `mod-redemption-code` 的兑换成功路径接入宣传兑换流水记录,不新增账号/角色绑定限制。
3. 为 `mod-reward-template` 的物品发放提供新增 item GUID 的可追踪结果。
4. 新建独立 Web API、玩家页面、管理员审核页面和图片存储适配器。
5. 先完成数据库迁移和模块单元/集成测试,再接入真实 Web 上传。
