# 模块性能审查与优化方案

> 审查日期：2026-06-11
> 范围：E:\azerothcore-wotlk\modules 下全部 68 个 mod-* 模块（约 17 万行 C++），逐模块源码审查
> 目标：找出性能瓶颈与问题代码，给出分阶段优化路线

---

## 一、总体结论

所有模块的性能问题高度集中在 **6 个共性反模式** 上。单独看每个模块都"还能跑"，但全部叠加后，主线程/地图线程在每次伤害、每次拾取、每次登录上都背着几十次哈希查找、字符串解析甚至同步数据库往返。

| # | 共性反模式 | 典型模块（最严重） | 影响 |
|---|-----------|------------------|------|
| 1 | **战斗热路径（OnDamage / ModifyMeleeDamage / ModifySpellDamageTaken / DOT tick）里做同步 DB 查询或全表线性扫描** | mod-shengwu_moban、mod-huanjinxitong、mod-wuhun-system、mod-vip-system、mod-magic-hit-system、mod-class-attributes、mod-rune-system、mod-xianmen-system、mod-abyss-cultivation | 每秒成百上千次伤害事件 × 每次查库/扫表 = 世界线程卡顿的最大来源 |
| 2 | **主线程同步 DB（Query / DirectExecute / SHOW TABLES）出现在登录、拾取、物品删除、Addon 请求路径** | mod-rune-system（每拾取一件物品查一次库）、mod-ascension-system 与 mod-xianmen-system（每次物品删除查库）、mod-item-recycle（每周期每背包物品查一次库）、mod-boundary（玩家数据零缓存）、mod-huanjinxitong（登录触发 item_instance 全库扫描） | 开服登录潮、AOE 刷怪拾取、一键卖物时全服可感卡顿 |
| 3 | **sConfigMgr->GetOption 出现在每伤害/每属性重算/每玩家每 tick** | mod-cut-system（最热）、mod-reincarnation（10 个属性 hook）、mod-heal-rune-system、mod-chenghao-system、mod-cultivation-system、mod-abyss-cultivation | 每次都是字符串构造 + map 查找，每秒数千~数万次纯浪费 |
| 4 | **全局容器无锁，被地图线程 hook 并发读写**（MapUpdate.Threads > 1 时为崩溃级风险） | mod-creature-attributes（共享 mt19937 + 多个 map）、mod-shengwu_moban、mod-aura-attributes、mod-map-attributes、mod-challenge-mirage、mod-chenghao-system、mod-player-attribute-panel、mod-auto-group、mod-abyss-cultivation、mod-xianmen-system、mod-magic-hit-system | 随机崩服 / 数据损坏 |
| 5 | **per-player / per-creature 数据无限增长，下线/死亡不清理** | mod-creature-attributes（4 个 map 永不清理）、mod-huanjinxitong（_creatureDeathHuanJingLevel）、mod-currency-system、mod-breakthrough（清理函数写了但从未调用）、mod-item-attributes / mod-item-skills 缓存、mod-popup-template | 长期运行内存持续上涨 |
| 6 | **hook 签名不匹配（缺 override / 名字不是 OnPlayer*）导致死代码** —— 功能静默失效，且一旦"修好"会立即引爆背后的查库/全表扫描 | mod-breakthrough（经验事件全死）、mod-event-trigger（事件触发器全死）、mod-item-with-ai（8 个钩子全死）、mod-item-commerce-system（限购全死）、mod-property-adjuster（整个模块无效）、mod-rune-system（缓存推送死代码） | 正确性 + 延迟性能炸弹 |

另有 3 个**独立的高危点**：

- **mod-remote-player-limit**：每 2 小时在世界主线程做同步 HTTP（DNS/connect 无超时），授权服务器不可达时**全服冻结数秒到数十秒**。
- **mod-skill-master**：注册了 ServerScript 的 CanPacketReceive，导致**全服每个入站数据包都多一次深拷贝**（含每秒上万的移动包）。
- **mod-mall-system**：Addon 消息 `REQUEST_ITEMS` 存在 **SQL 注入**（玩家可控字符串直接拼进 WorldDatabase 查询），同时每次请求绕过内存缓存同步查库。

## 三、分阶段优化路线

### 阶段 1：止血（崩溃风险 + 全服冻结级，建议 1 周内完成）

1. **mod-remote-player-limit**：HTTP 移到后台线程（std::thread + 原子变量回写），世界线程只读结果。
2. **mod-aura-attributes**：遍历光环时先收集待移除 ID，循环外统一 RemoveAura；触发加"已处理"标记；std::stoul 改 `Acore::StringTo`。
3. **mod-quest-reward-attributes**：加载时先 `reserve()` 或改存下标，消除悬垂指针；延迟重应用队列按玩家去重。
4. **mod-cultivation-system**：chain boss lambda 捕获裸 `Unit* killer` 改为捕获 ObjectGuid（use-after-free）。
5. **线程安全批量整改**（若开启 MapUpdate.Threads>1 则必须，否则可降级到阶段 3）：
   - mod-creature-attributes：mt19937 改 `thread_local` 或核心 `urand`；血条/真伤/移动计时器 map 加锁或挂到 Creature 对象。
   - mod-shengwu_moban damageRecords、mod-map-attributes / mod-challenge-mirage / mod-chenghao-system / mod-player-attribute-panel / mod-auto-group 的全局玩家容器：加 shared_mutex 或下沉到 Player/Creature 对象。
   - mod-huanjinxitong / mod-abyss-cultivation / mod-magic-hit-system / mod-xianmen-system 的静态无锁 map 同理。
   - mod-auto-group：`uint32 _checkTimer` 下溢修复（改 int32），裸 Player* 改 ObjectGuid。
6. **mod-mall-system**：SQL 注入修复（改走内存缓存即可顺带消灭注入面）。
7. **mod-skill-master**：去掉 ServerScript 拦包，改用 gossip/训练师钩子。

### 阶段 2：消灭战斗热路径的查库与全表扫描（收益最大，建议 2-3 周）

统一手法：**"加载/变更时一次性计算并缓存，热路径只读 O(1)"**。

1. **mod-shengwu_moban**：`_生物_伤害排行`、随机模板、经验配置三张表启动时整表载入 `unordered_set/map`，OnDamage/spawn/击杀路径零查库。
2. **mod-huanjinxitong**：生物被调整时把匹配配置/减伤/真伤缓存到 per-creature 结构，伤害 hook O(1)；SHOW TABLES 结果缓存；SaveItemAttributeEnhancement 改异步。
3. **mod-vip-system**：删除 `VipPrivilegeScript` 重复钩子，全部走内存缓存 `GetPlayerVipInfo`（顺带修复倍率平方 bug）。
4. **mod-wuhun-system**：御灵等级、装备倍率缓存进 PlayerWuhunData / WuhunEquipmentSlot，由源模块变更时主动失效。
5. **mod-xianmen-system**：GetEffectiveSkills 结果按玩家缓存（技能/门派变更时失效）；调试签名与 LOG_INFO 全部包进 debug 开关；ModifyMeleeDamage/SpellDamage 入口先对"双方都非仙门玩家"短路。
6. **mod-magic-hit-system**：构建 `unordered_set<spellId>` 让 HasSpellConfig O(1)；登录预热缓存，热路径未命中直接返回；castHits 上限收紧到 20-50。
7. **mod-rune-system**：删除拾取/创建物品钩子的查库与日志；登录改一条按角色 GUID 的批量查询；符文 itemId→runeId 建索引；per-player 法术加成预计算缓存。
8. **mod-class-attributes**：规则应用时预合成 6 个倍率到 PlayerAttributeModifier，4 个伤害 hook 变 O(1)。
9. **mod-ascension-system / 仙门仙器**：CanItemRemove 改查内存 `unordered_set`（登录时加载占用 GUID 集合）。
10. **mod-item-recycle**：材料仓库保留集合登录时载入内存；GetPlayerRecycleSettings 返回指针不拷贝。
11. **mod-creature-attributes**：生物 spawn 时掷一次随机并缓存配置指针；moveToCoords/randomMoveDistance 等字符串字段加载时预解析。
12. **mod-abyss-cultivation**：遗物加成汇总、scriptGroup→scale 映射按玩家缓存；OnAllCreatureUpdate 先用 boss entry 哈希集过滤；近战 proc 从 OnPlayerApplyWeaponDamage 迁到真正的战斗事件钩子。
13. **热路径 GetOption 批量整改**（一次性全仓库 grep 处理）：mod-cut-system、mod-reincarnation、mod-heal-rune-system、mod-chenghao-system、mod-cultivation-system、mod-talent-soul、mod-fashion-system、mod-treasure-box、mod-abyss-cultivation 等，统一在 `OnAfterConfigLoad` 缓存为 bool/数值成员。

### 阶段 3：登录路径、写库节奏与 Addon 防刷（2 周）

1. **登录同步查询合并/异步化**（几乎所有模块各查 1-4 次，叠加 = 登录潮卡顿）：
   - 优先级最高：mod-huanjinxitong（登录触发 item_instance 全库扫描清理 → 移到独立定时任务并异步分批）、mod-item-sets（启动 N+1 查询改 JOIN；登录双重加载去重）、mod-rune-system / mod-item-enhancement（逐件装备查询改批量）、mod-xianmen-system / mod-ascension-system（ValidateEquippedItems 改 `WHERE guid IN (...)` 或直接信任 JOIN 结果）。
   - 中期方向：参照核心 LoginQueryHolder 建一个统一的"模块登录异步预载"框架。
2. **写库节奏统一**："DirectExecute → 异步 Execute；逐条写 → 事务/批量；每事件全量保存 → 脏标记 + 定时(30-60s)/登出保存"。
   - 范本：mod-talent-soul 的 `_dirtyPlayers` + 5 秒 FlushDirtyPlayerData（全仓库唯一正确实现，照抄即可）。
   - 待改：mod-item-growth（SavePlayerItemRecord DirectExecute）、mod-hardcore-mode（死亡路径连续两次 REPLACE）、mod-item-attributes / mod-item-skills（DirectExecute）、mod-wuhun-system（每杀 Boss 全量保存）、mod-currency-system（每次货币变动 SELECT+DirectExecute）、mod-heal-rune-system / mod-chenghao-system（DirectExecute）、mod-boundary、mod-item-sets（登出 DELETE+逐条 INSERT 无事务）、mod-redemption-code（批量生成 1 万码 = 1 万次同步往返，改本地去重+事务批量）、mod-tujian-system（一键收集逐条 REPLACE）。
3. **Addon/命令请求防刷**（客户端可任意频率触发的同步查库 = DoS 面）：
   - 统一原则：内存即权威，REQ_* 一律读缓存；每玩家加 1 秒节流。
   - 涉及：mod-wuhun-system(REQ_EQUIP)、mod-cut-system、mod-heal-rune-system、mod-chenghao-system、mod-boundary(INFO)、mod-challenge-mirage(LIST)、mod-huanjinxitong(HUANJING_QUERY)、mod-teleport-system（`.传送 去` 的同步 LIKE 全表扫描改内存匹配）、mod-vip-system（UI 配置表常驻缓存）、mod-item-sets（tooltip 触发的检查命令）、mod-breakthrough（排名 COUNT 子查询加索引/定时缓存）。
4. **公共基础设施索引化**（被所有玩法模块调用，低效被放大）：
   - mod-requirement-template：鉴定/属性/技能等级判定改内存缓存（现在是逐背包物品同步查库）；24 个 string 的模板结构改 shared_ptr 返回；表达式加载期预解析；ConsumeRequirements 加回滚。
   - mod-reward-template：GetRewardTemplate 建 unordered_map 索引；random_device/mt19937 改 `roll_chance_f`。
   - mod-item-attributes：负缓存（空结果也缓存）；按 attributeType 建模板索引；读路径去深拷贝。

### 阶段 4：内存治理与死代码清理（1 周）

1. **登出/死亡清理**：为以下容器补 OnPlayerLogout / OnCreatureRemoveWorld 清理 —— mod-creature-attributes（4 个 map + 鉴定记录）、mod-huanjinxitong（_creatureDeathHuanJingLevel）、mod-currency-system、mod-breakthrough（接上从未被调用的 CleanupPlayerExpCache）、mod-popup-template（3 个容器）、mod-item-attributes / mod-item-skills / mod-magic-hit-system 的物品缓存、mod-xianmen-system 调试签名 map、mod-skill-master sessions、mod-item-with-ai 冷却表、mod-vip-system _playerVipData。
2. **死代码 / 失效钩子处置**（修复前必须先完成对应的缓存化，否则修好即引爆）：
   - mod-breakthrough 经验事件（修复前先做经验配置缓存）、mod-event-trigger 全部事件钩子（先建类型索引 + per-player 计时）、mod-item-with-ai 8 个钩子（先做 CSV 预解析 + id 索引 + urand）、mod-item-commerce-system 限购（先整表缓存 + 内存计数）、mod-property-adjuster（改继承 AllCreatureScript）、mod-rune-system OnLogin/OnLogout、mod-skill-control 空 Register() 的 SpellScript。
   - 建议全仓库模块统一开 `-Wsuggest-override` 编译警告，杜绝此类问题再次发生。
3. **杂项清理**：删除未编译的旧文件（mod-auto-loot 三套 loader、mod-item-with-ai 的 ItemWithAILoader.cpp、mod-item-attributes 的死命令文件）；random_device/mt19937 每次重建统一改 thread_local 或核心随机接口；高频 LOG_INFO 统一降 LOG_DEBUG（rune/breakthrough/mall/material-warehouse/item-with-ai/announcement/xianmen）。

### mod-eluna 专项说明

模块与上游官方 master 同步、已含 enabled-hook-lists 优化，本地仅有 int64 金币适配 patch，质量良好。注意三点：
1. 单 Lua 状态 + 全局递归锁是架构天花板：开多线程地图后所有 Lua 串行，**严禁脚本内同步 SQL、慎用 ON_PACKET_SEND / 生物 AIUPDATE 等高频全局事件**。
2. 上游 bug：Unit/GO 的 elunaEvents 每 tick 被 Update 两次（Lua 定时器约 2 倍速触发），值得本地打补丁并反馈上游。
3. 若生产环境不跑 Lua 脚本，建议从编译中剔除而不是 `Eluna.Enabled=false`（关闭后每对象的处理器分配与锁操作仍存在）。
