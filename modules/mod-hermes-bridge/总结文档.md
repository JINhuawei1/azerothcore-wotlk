## 1. 项目目标

`mod-hermes-bridge` 的目标是在本地 AzerothCore 服务器与固定版本 WoW 3.3.5 客户端之间建立一条可控、可验证、可扩展的双向通信桥。

最终希望达到的效果是：

1. 客户端 Lua 可以通过类似 `/hdll send xxx` 的命令向服务器发送自定义消息。
2. 服务器通过自定义 CMSG opcode 接收消息，解析出 channel、协议版本和 payload。
3. 服务器根据 payload 执行业务逻辑，并通过自定义 SMSG opcode 回包。
4. 客户端 native DLL 捕获服务器 SMSG 回包，将 payload 分发回 Lua 层。
5. Lua 层可以通过 inbox、callback 或后续 UI 逻辑消费服务器响应。
6. 整个链路有自动化验证脚本，能快速确认：客户端未崩溃、服务器收到正确 payload、客户端收到正确 response、没有 malformed/unknown opcode。

该模块当前不是普通插件式 Lua addon，而是“服务端自定义 opcode + 客户端 native DLL hook + Lua API”的组合桥接方案。

## 3. 自定义 Opcode 与协议格式

### 3.1 Opcode 注册

当前已在 AzerothCore opcode 表中加入：

```cpp
CMSG_HERMES_BRIDGE = 0x990
SMSG_HERMES_BRIDGE = 0x991
```

对应注册位置：

- `src/server/game/Server/Protocol/Opcodes.h`
  - `CMSG_HERMES_BRIDGE = 0x990`
  - `SMSG_HERMES_BRIDGE = 0x991`

- `src/server/game/Server/Protocol/Opcodes.cpp`
  - `CMSG_HERMES_BRIDGE` 绑定到 `WorldSession::HandleHermesBridgeOpcode`
  - `SMSG_HERMES_BRIDGE` 作为服务器发包 opcode

### 3.2 CMSG/SMSG 共同 payload 格式

当前已直接升级为 Hermes Frame v2，不保留 v1 legacy 入口。

客户端 native 发送时，实际进入 upper-send 的 buffer 是：

```text
opcode:uint32 = 0x0990
magic:uint16 = 0x4842
version:uint8 = 2
headerSize:uint8 = 24
lane:uint8
messageType:uint8
codec:uint8
flags:uint8
schemaId:uint16
methodId:uint16
requestId:uint32
sequence:uint32
payloadSize:uint32
payload bytes
```

SMSG `0x0991` 回包使用同一帧头。upper-send 内部继续负责走客户端原生加密/封包路径。

### 3.3 服务端解析规则

`HermesBridgeHandler.cpp` 当前逻辑：

1. 检查首字段 `magic == 0x4842`，非 v2 直接丢弃。
2. 读取 Hermes Frame v2 header。
3. 校验：
   - `version == 2`
   - `headerSize >= 24`
   - `payloadSize <= 64 * 1024`
   - `payloadSize <= remaining`
   - 暂不支持 `compressed/fragmented` flags
   - 当前只处理 `messageType=request` 与 `codec=json`
4. 读取 JSON-RPC payload。
5. 使用 jsoncpp 解析请求，并通过 `HERMES_METHOD_REGISTRY` 查找 method handler。
6. 用 Hermes 专用 JSON 字符串构造响应，回发 Hermes Frame v2 + JSON-RPC response。
   - 注意：当前不使用精简版 jsoncpp `FastWriter` 生成回包；该路径已确认会导致 worldserver 崩溃。

当前已实现的 JSON-RPC method：

```text
hermes.hello
hermes.ping
hermes.debugEmit
hermes.debugBinaryEmit
hermes.debugVitalsBinaryEmit
hermes.debugBulkChunkEmit
hermes.getSchemaRegistry
hermes.getMethodRegistry
server.getStatus
server.getNumericLimits
player.getBasicInfo
player.getPosition
player.getVitals
player.getSnapshot
```

当前正式 DLL：`client/hermes_bridge_dll.c`，版本 `v0.7.11-v2`。

### 4.1 已确认客户端版本和关键地址

已确认信息：

```text

ImageBase: 0x00400000
无 ASLR
FrameScript::Execute: 0x00819210
```

当前使用的关键地址：

```text
FrameScript::Execute:            0x00819210
Packet factory:                  0x00467540
Upper send path:                 0x004675F0
Receive after-opcode hook point: 0x00632001
Lua SendAddonMessage handler:    0x00500560
Lua string helper:               0x0084E0E0
```

### 4.2 upper-send hook

作用：

1. hook 客户端 upper-send 函数 `0x004675F0`。
2. 捕获当前 session 的 connection `self`。
3. 将 `self` 保存到 DLL 全局状态。
4. 后续 native send 复用该 `self` 发送自定义 CMSG。

关键经验：

- `self` 是每次登录/重启客户端后的 session 状态，不能硬编码长期使用。
- 如果 `wow.exe` 重启，必须重新捕获。
- 不应直接用 Winsock `send()` 绕过客户端加密路径，否则服务端会收到 malformed/framing 错误。

### 4.3 native CMSG 发送路径

发送流程：

1. 组装 opcode-first payload：

```text
0x0990:uint32
Hermes Frame v2 header
JSON-RPC payload bytes
```

2. 调用客户端 packet factory：

```text
0x00467540
```

3. 去掉 packet factory 生成 buffer 前面的 2 字节 size header：

```text
packetBuffer = *(DWORD*)(packet + 0x08) + 2
packetLength = *(DWORD*)(packet + 0x0C) - 2
```

4. 构造兼容 upper-send 的 sendObject。
5. 调用 upper-send：

```text
0x004675F0(connectionSelf, sendObject, 0)
```

成功日志示例：

```text
HermesBridge native v2 send result=0 methodId=2 requestId=1001 bytes=82
```

### 4.4 receive after-opcode hook

作用：

1. hook `0x00632001`，此处 opcode 已被客户端读取。
2. 判断 `ESI` 中 opcode 是否为 `0x0991`。
3. 如果是 `SMSG_HERMES_BRIDGE`，解析 packet 中 payload。
4. 写日志并把 response 复制进 native recv ring buffer。
5. WoW 主窗口 timer 在主线程批量泵队列，再调用 Lua：

```lua
HermesDLL._NativeReceive(lane, payload)
```

当前确认的 SMSG payload 起点：

```text
([packet+0x04] - [packet+0x08]) + [packet+0x14]
```

解释：

- `[packet+0x04]` 为 buffer base。
- `[packet+0x08]` 为 buffer bias。
- `[packet+0x14]` 为 cursor。
- 对于当前 `SMSG 0x0991`，cursor 通常为 `2`，因为 opcode 已被 dispatch 路径消费。

成功日志示例：

```text
HermesBridge recv v2 lane=1 type=2 codec=1 bytes=96
HermesBridge recv v2 methodId=2 requestId=1001 seq=1 self=0x1260AE58
{"jsonrpc":"2.0","id":1001,"result":{"pong":true,"payload":"ping-v2-matrix"}}
HermesBridge recv pump main-thread pumped=1 pending=0
```

### 4.5 SendAddonMessage hook 与 `/hdll send` / `/hdll rpc`

当前 Lua 到 native 的本地触发入口：

1. DLL 注入 Lua API。
2. Lua 中注册 slash command：

```text
/hdll send <payload>
/hdll rpc <method> <payload>
```

3. slash handler 调用：

```lua
HermesDLL.Send('debug', payload)
HermesDLL.Request(method, payload)
```

4. `HermesDLL.Send` / `HermesDLL.Request` 内部调用：

```lua
SendAddonMessage('HERMESDLL', payload, 'WHISPER', UnitName('player'))
SendAddonMessage('HERMESDLL', 'rpc '..method..' '..payload, 'WHISPER', UnitName('player'))
```

5. native DLL hook `SendAddonMessage`。
6. 只拦截 prefix 为 `HERMESDLL` 的消息。
7. 拦截后不在 Lua C-function hook 内直接发送，而是：
   - 复制 payload 到 DLL 全局 buffer。
   - 启动一个短延迟 worker thread。
   - hook 函数立即返回 `0`。
   - worker thread 再调用 native send。

这样做的原因：

- 早期测试发现，在 `SendAddonMessage` Lua C-function hook 内直接调用 native send 虽然能到达服务器，但可能在 Lua/addon-message 栈回退时导致客户端崩溃或退出。
- 延迟 worker 方式已经实测稳定。

成功日志示例：

```text
HermesBridge SendAddonMessage hook installed
HermesBridge SendAddonMessage intercepted hit=1 bytes=30
HermesBridge native v2 send result=0 methodId=2 requestId=1002 bytes=88
HermesBridge recv v2 lane=1 type=2 codec=1 bytes=77
{"jsonrpc":"2.0","id":1002,"result":{"pong":true,"payload":"ping-v2-matrix"}}
```

回包进入 Lua 后会：

4. 按 `pending.method`、通用 `response`、`error/message` 事件触发 `HermesDLL.Emit(...)`。
5. 如果没有 request callback 或事件 handler 消费，则回退调用 `HermesDLL.Dispatch(channel, payload)`。
6. `HermesDLL.PrunePending(maxAge)` 可清理超时请求，默认超时基线为 15 秒。

## 7. 待完成目标

### 7.1 协议层待完善

当前 v2 外层已经具备 `lane/messageType/codec/flags/schemaId/methodId/requestId/sequence/payloadSize`，控制面已使用 JSON-RPC。后续协议层重点不再是“补字段”，而是把这些字段的语义和高频路径落地。

后续建议：

1. requestId / correlationId 在 Lua 层落地
   - v2 frame 已有 `requestId`。
   - 下一步需要 Lua pending map 匹配请求与响应。
   - 支持并发请求、超时重试和 callback。

2. messageType / lane 语义固化
   - v2 frame 已有 `messageType` 和 `lane`。
   - 下一步需要明确 `request/response/event/error/ack/chunk` 的处理策略。
   - `rpc` lane 已可用，`event/snapshot/bulk/debug` 仍需业务落地。

3. errorCode 规范
   - 当前使用 JSON-RPC error object。
   - 需要固定 `hermesCode` 枚举，例如：`INVALID_REQUEST`、`METHOD_NOT_FOUND`、`PLAYER_NOT_READY`、`UNSUPPORTED_CODEC`。

4. lane / methodId 命名规范
   - v2 外层使用 `lane` 区分 control、rpc、event、snapshot、bulk、debug。
   - 低频 RPC 使用 JSON-RPC `method` 字符串。
   - 高频路径使用 `methodId/eventId/schemaId` 数字 ID，避免字符串开销。

5. payload 编码格式
   - 当前控制面 payload 是 JSON-RPC。
   - 后续不应升级为“纯 JSON 协议”。
   - 推荐固定外层 Hermes Frame v2，内部按 lane/codec 区分控制面、RPC、事件、快照和大数据。
   - JSON-RPC 只用于控制面、低频 RPC、调试和可读性要求高的数据。
   - 高频血量、伤害、资源、Boss 机制等数据走二进制 schema + 批量推送。

   - 确认 `HermesDLL.lastReceive` 正确。

## 8. 已知坑点与处理方式

### 8.1 MSYS/Git Bash 参数转换

在本机 Hermes 环境中，terminal 使用 Git Bash/MSYS，而不是 PowerShell。

注意：

```bash
cmd.exe /c xxx
```

可能被 MSYS 路径转换干扰。

推荐：

```bash
cmd.exe //c xxx
```

类似问题还包括：

```bash
taskkill.exe /PID ...
```

可能被转换成错误路径。

推荐：

```bash
cmd.exe //c taskkill //PID <pid> //T //F
```

### 8.2 DLL 路径复用导致 DllMain 不重跑

Windows 已加载过同一路径 DLL 后，再次 `LoadLibraryA` 同一路径通常不会重新执行 `DllMain`。

因此：

- bridge DLL 每次验证要唯一文件名。
- trigger DLL 每次验证要唯一文件名。
- restore DLL 也必须唯一文件名。

之前出现过假象：restore DLL 复用旧路径，`LoadLibraryA` 返回成功，但 `DllMain` 没重跑，导致旧 hook 没恢复，新 bridge DLL 显示：

```text
HermesBridge upper send hook install failed
HermesBridge recv hook install failed
HermesBridge SendAddonMessage hook install failed
```

现在 verifier 已修复：每次构建唯一 restore DLL。

### 8.3 SendAddonMessage hook 必须恢复

早期 restore 只恢复：

```text
0x004675F0
0x00632001
```

但没有恢复：

```text
0x00500560
```

这会导致新 DLL 的 `SendAddonMessage hook install failed`。

当前 restore helper 已恢复三处地址。

### 8.4 不要在 SendAddonMessage hook 内直接发送

直接在 Lua C-function hook 内调用 native send 可能导致客户端崩溃。

当前正确做法：

1. hook 内复制 payload。
2. 创建延迟 worker thread。
3. hook 立即 return。
4. worker 再调用 native send。

### 8.5 不要 hook 高频 packet read helper

早期 receive 调试中发现 hook packet read helper 容易 reentrancy/崩溃。

当前安全方案：

```text
hook 0x00632001 after-opcode dispatch point
```

只读取稳定寄存器和 packet 字段，不调用 packet read helper。

- 旧 bridge 在 recv hook 中对 RPC lane 同步调用 `FrameScript::Execute`。

- v2 response 全部先进入 native recv ring buffer。
- WoW 主窗口 `SetTimer` 在主线程每 16ms 批量 pump，最多 64 条。
- trigger DLL 只负责注册主窗口 timer，不再后台线程直接执行 Lua。
- 单独 `player.getSnapshot`、十个基础 RPC + JSON/binary event lane matrix、`HERMES_BURST_COUNT=32` live 验证均通过，且没有新增 `Errors` 文件。

## 11. 全面接管插件通信层的实现目标

本节是后续开发需要明确实现的目标：`mod-hermes-bridge` 不只是做一个调试桥，而是逐步成为“全面接管插件与服务端通信”的底层通道。

### 11.1 全面接管后的总体效果

全面接管后，插件侧不再依赖原生 addon message 作为真正网络通信层，而是只把它作为本地触发入口，甚至后续可以完全替换为 native Lua 函数。

目标效果：

1. 插件 Lua 调用统一 API：

```lua
HermesBridge.Request("GetPlayerCustomStats", {}, function(response)
    -- 更新面板、血条、资源条、战斗浮字等 UI
end)
```

2. DLL 负责把 Lua 请求转成自定义 CMSG：

```text
CMSG_HERMES_BRIDGE 0x0990
```

3. 服务端模块负责解析 command、权限、参数并返回结果。
4. 服务端可以主动推送自定义事件：

```text
CustomDamage
CustomHealthUpdate
CustomResourceUpdate
BossMechanicUpdate
ModuleStateChanged
```

5. 客户端 DLL 捕获：

```text
SMSG_HERMES_BRIDGE 0x0991
```

6. Lua 层通过 callback、event handler、inbox 或 UI 组件消费数据。

最终形态类似一套专用 RPC/事件总线：

```text
Lua UI / Addon
 -> Hermes Lua API
 -> Native DLL
 -> CMSG_HERMES_BRIDGE
 -> AzerothCore command dispatcher
 -> SMSG_HERMES_BRIDGE
 -> Native receive hook
 -> Lua callback / UI update
```

### 11.2 关于 addon 255 字节限制

原生 `SendAddonMessage` 通常存在单条消息约 255 字节级别的限制，并且会受到聊天/addon message 系统频率、通道、分包拼包的限制。

当前桥接方案的目标是突破这个限制：

- `/hdll send` / `/hdll rpc` 当前仍借用 `SendAddonMessage('HERMESDLL', ...)` 作为 Lua 到 DLL 的本地触发入口。
- DLL hook 到 prefix `HERMESDLL` 后会拦截该调用，不让它继续走原生 addon 网络通道。
- 真正客户端到服务端的数据走自定义 opcode `CMSG_HERMES_BRIDGE 0x0990`。
- 服务端当前协议字段 `payloadSize` 是 `uint32`，并在服务端限制最大 payload 为 `64 * 1024`。

因此结论是：

| 场景 | 是否受 255 字节限制 |
|---|---|
| 原生 addon 直接发消息 | 是 |
| 当前 `/hdll send` 作为本地触发入口 | 入口层仍建议不要传超长文本 |
| DLL 拦截后走 `CMSG 0x0990` | 不受原生 addon 255 字节限制 |
| 未来 native Lua C API 直接发送 | 可以彻底绕开 `SendAddonMessage` 入口限制 |

后续目标：注册更直接的 native Lua 函数，例如：

```lua
HermesNativeSend(channel, payload)
```

这样 Lua 到 DLL 的入口也不再受 `SendAddonMessage` 的参数/语义限制。

### 11.3 性能目标

全面接管后，性能理论上会明显优于传统 addon message 通信，原因是：

1. 不再走聊天/addon message 网络通道。
2. 不需要大量 255 字节分包/拼包。
3. 可以批量推送数据。
4. 可以使用二进制协议，减少字符串和 JSON 开销。
5. 可以按业务设计专用消息结构。
6. 可以由服务端主动推送，不需要客户端高频轮询。

但也需要控制新的瓶颈：

- Lua UI 刷新频率。
- 服务端推送频率。
- native hook reentrancy 风险。
- payload 编码/解码成本。
- 客户端 Lua 大量创建字符串/table 的 GC 压力。

建议性能策略：

| 数据类型 | 建议方式 |
|---|---|
| 低频配置/面板数据 | JSON request/response |
| 中频状态数据 | 批量 JSON 或轻量二进制 |
| 高频血量/资源/伤害事件 | 二进制事件 + 批量 + 限频 |
| 大数据列表 | 分页/分片/缓存 |
| UI 刷新 | 10~20Hz 足够，不要每帧无脑刷新 |

对于血量、伤害、资源等高频数据，建议服务端按事件或阈值推送，而不是每个 server tick 都推。

### 11.6 推荐的多 lane 数据通道设计

后续全面接管建议采用“控制面 JSON、数据面二进制”的多 lane 通道。核心原则是：外层 Hermes Frame 固定，内层 payload 按 lane 和 codec 选择 JSON-RPC、二进制 schema 或分片大数据。

#### 11.6.1 Hermes Frame v2 外层头

推荐 v2 帧头：

```text
magic:uint16        // Hermes v2 magic
version:uint8       // 2
headerSize:uint8    // 当前 24，允许后续扩展
lane:uint8          // control/rpc/event/snapshot/bulk/debug
messageType:uint8   // request/response/event/error/ack/chunk
codec:uint8         // json=1, msgpack=2, binary=3
flags:uint8         // compressed/fragmented/batched/urgent
schemaId:uint16     // 二进制结构版本
methodId:uint16     // 高频路径使用数字 ID，避免字符串开销
requestId:uint32
sequence:uint32
payloadSize:uint32
payload bytes
```

v2 帧头目标：

- 未来升级时保持外层不再大改。
- 低频数据可以保持 JSON 可读。
- 高频数据不经过 JSON 字符串解析。
- 支持批量、分片、压缩、优先级、ACK 和乱序检测。
- 客户端和服务端都能按 lane 做限速、丢弃、合并和排队策略。

#### 11.6.2 Lane 规划

推荐 lane：

| Lane | 用途 | 推荐 codec | 丢弃策略 |
|---|---|---|---|
| control | 握手、版本、能力协商、订阅 | JSON-RPC | 不丢 |
| rpc | 低频请求响应，如角色信息、背包、排行榜 | JSON-RPC，后续可 MsgPack | 不丢，有超时 |
| event | 服务端主动事件，如自定义伤害、Boss 机制 | Binary | 可批量，按事件类型限频 |
| snapshot | 血量、资源、护盾、状态快照/增量 | Binary | 同一对象旧值可覆盖 |
| bulk | 大数据列表、图鉴、排行榜分页 | Chunked binary/JSON | 不丢，支持重传 |
| debug | 开发期调试文本和日志回显 | JSON/text | 可限流 |

#### 11.6.3 控制面与 RPC：JSON-RPC 2.0

控制面和低频 RPC 使用 JSON-RPC 2.0，原因是 request、response、error、notification 语义完整，Lua/C++ 都容易调试。

请求示例：

```json
{
  "jsonrpc": "2.0",
  "id": 1001,
  "method": "player.getBasicInfo",
  "params": {}
}
```

响应示例：

```json
{
  "jsonrpc": "2.0",
  "id": 1001,
  "result": {
    "name": "Player",
    "level": 80,
    "mapId": 571
  }
}
```

错误示例：

```json
{
  "jsonrpc": "2.0",
  "id": 1001,
  "error": {
    "code": -32601,
    "message": "Method not found",
    "data": {
      "hermesCode": "UNKNOWN_METHOD",
      "method": "player.getBasicInfo"
    }
  }
}
```

#### 11.6.4 高频数据面：二进制 schema

高频血量、伤害、资源、Boss 机制不走 JSON。推荐用 `schemaId + methodId/eventId` 定义二进制结构，并批量发送。

自定义伤害批量事件示例：

```text
eventId:uint16 = CustomDamage
count:uint16
repeated count times:
  sourceGuid:uint64
  targetGuid:uint64
  amount:uint32
  flags:uint16      // crit/block/absorb/custom school 等
  timeDelta:uint16
```

自定义血量/资源快照示例：

```text
snapshotId:uint16 = UnitVitals
count:uint16
repeated count times:
  unitGuid:uint64
  currentHp:uint32
  maxHp:uint32
  shield:uint32
  customPower:uint32
  flags:uint16
```

高频策略：

- 服务端批量推送，不一条事件一个包。
- 状态类数据使用 snapshot + delta，同一对象旧值可以覆盖。
- Lua UI 不直接在网络 hook 内刷新，而是通过 native queue + Lua Pump 分批消费。
- UI 刷新频率控制在 10~20Hz，不按 server tick 无脑刷新。
- 每个事件类型独立限频，避免一个系统拖垮整个桥。

#### 11.6.5 客户端消费模型

长期目标不要在 receive hook 深处直接执行复杂 Lua。推荐：

```text
network hook
 -> native ring buffer / priority queue
 -> Lua OnUpdate 或定时器调用 HermesDLL.Pump(maxEvents, maxMs)
 -> Lua 分发 callback/event handler
 -> UI 按预算刷新
```

队列策略：

- RPC response 不能丢。
- control/bulk chunk 不能丢。
- snapshot 可合并同一对象旧值。
- debug 可限流。
- event 可按类型限速和批量。

这样后续即使接入大量自定义 UI、血量、伤害、资源、Boss 机制，也不需要再次推翻外层协议。

### 11.7 全面接管后的实际应用场景

后续可以实现的具体功能包括：

1. 自定义角色属性面板。
2. 自定义伤害统计面板。
3. 自定义战斗浮字。
4. 自定义 Boss 机制 UI。
5. 自定义血条/护盾/资源条 overlay。
6. 仙门系统、合成系统、装备系统等服务端模块 UI 通信。
7. 服务端主动推送任务/副本/活动状态。
8. 客户端请求服务端查询物品、角色、排行榜、货币等数据。
9. GM/调试工具面板。
10. 模块热更新状态提示。

### 11.8 该目标的边界和注意事项

需要明确：全面接管的是“插件与服务端之间的数据通信层”，不是第一阶段就替换 WoW 客户端全部原生系统。

推荐边界：

- 可以做自定义 UI overlay。
- 可以做自定义数据展示。
- 可以做服务端事件推送。
- 可以做插件 RPC。
- 可以做模块专属协议。

暂不建议第一阶段做：

- 强改客户端原生 UnitHealth。
- 强改客户端原生 combat log。
- 伪造复杂原生战斗包。
- 高频无节制推送所有单位状态。
- 在网络 dispatch hook 内执行复杂 Lua 逻辑。

正确方向是先建立稳定、可测、可扩展的数据桥，再逐步把具体 UI 和业务模块迁移到这条桥上。
